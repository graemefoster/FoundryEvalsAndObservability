# From prompt to production: presenter playbook

A purchasing-advice agent in Microsoft Foundry, taken from a first prompt to a gated release.
The deck is `presentation/deck.html` (or `presentation.pptx`). This page tells you what to
prepare, what to show in each demo, and how to run everything yourself.

## The agent

`purchasing-advice-demo`: Microsoft Agent Framework, GPT-5.4-mini (low reasoning), hosted in
Foundry. It **advises**; it can't approve, buy or contact anyone. Its three tools are local
stand-ins shaped like the Microsoft IQ tools:

| Tool | Stands in for | Answers |
| --- | --- | --- |
| `knowledge_base_retrieve` | Foundry IQ | Policies: what must happen (quotes, approval roles, rules) |
| `ask` | Work IQ | People, right now: who holds a role, who's on leave, recorded delegations, messages |
| `search_ontology` | Fabric IQ | Business state: the department's budget (a fixed value) |

> Policy tells you **who must approve**. Work IQ tells you **who that is today**.

## What's where

| Path | Contents |
| --- | --- |
| `sample/agent/` | Agent code, baseline config (`.agent_configs/baseline/`), data in `data/` |
| `sample/agent/data/roster.json` | Work IQ directory (generated): managers, leave, delegations |
| `sample/evaluation/datasets/` | The three test sets (below) |
| `sample/evaluation/optimize.yaml` | The optimiser run |
| `sample/evaluation/overfitting-demo/` | The first optimiser run, kept as an exhibit of overfitting |
| `.github/workflows/` | PR gate, merge-to-main holdout, release gate |

**The three test sets.** All are generated by `evaluation/generate_approver_data.py`, which
computes every reference answer from the roster, so answers can't contradict the data.

| Set | File | Questions | Used by |
| --- | --- | --- | --- |
| Development | `approvers-development.jsonl` | 30 | Optimiser training; PR gate |
| Holdout | `approvers-holdout.jsonl` | 18 | Optimiser validation (Foundry calls it `validation_dataset`); merge to main |
| Drift | `approvers-drift.jsonl` | 8 | Release gate only. Never give it to the optimiser. |

Development and holdout use different departments, people and dates, so memorising a
name can't win. Drift changes facts a prompt could have memorised (a manager goes on leave,
a delegate changes).

## Before the talk

Evaluations take 5-10 minutes and optimisation about an hour, so run everything beforehand
and show saved results on stage.

1. **Set up the terminal** (from `sample/`):
   ```bash
   source .venv/bin/activate
   export FOUNDRY_PROJECT_ENDPOINT="$(azd env get-value FOUNDRY_PROJECT_ENDPOINT)"
   export DEMO_REPLAY_DIR="$HOME/demo-transcripts"   # outside the repo
   mkdir -p "$DEMO_REPLAY_DIR"
   ```
2. **Deploy:** `azd deploy purchasing-advice-demo`
3. **Run the baseline evaluation**, capturing the output for the replay:
   ```bash
   EVAL_DATASET=evaluation/datasets/approvers-holdout.jsonl \
     python evaluation/evaluate.py --wait 2>&1 | tee "$DEMO_REPLAY_DIR/evaluation.txt"
   ```
4. **Run the optimiser** (about an hour):
   ```bash
   azd ai agent optimize --config evaluation/optimize.yaml --no-prompt 2>&1 \
     | tee "$DEMO_REPLAY_DIR/optimisation.txt"
   ```
   Optional: to show overfitting as well, also run
   `evaluation/overfitting-demo/optimize.yaml`. It trains on 8 near-identical questions,
   which makes memorising tempting. Allow another hour. Results vary between runs, so
   review both before deciding what to show.
5. **Prepare the red PR for Demo 6:** a branch whose `.agent_configs/baseline/instructions.md`
   is a fact-stuffed candidate, for example candidate_1 from the overfitting run. Open the PR
   and let the gate fail once, so the failed check is ready to show.
6. **Check the replays:** `python evaluation/demo_replay.py check` should say OK for both.
7. **Open the browser tabs:** the agent in Foundry, a trace, the evaluation run, both
   optimisation runs (the overfitting one and the approver one), and the red PR.

## On stage

### Demo 1: Model choice

In Foundry, compare two or three models side by side, then show a Model Router deployment.
**Point:** the first model is a hypothesis; evaluations are what let you change it later.

### Demo 2: Run the starting agent

```bash
azd ai agent invoke purchasing-advice-demo --new-session --new-conversation \
  'Today is 13 October 2026. Can I book a team dinner for six this Thursday? It is about $540 all-in, and my manager has approved it.'
```

Use single quotes so the shell keeps `$540`. Then reply in the same conversation:
*"Yes, there will be wine."* Answers vary from run to run, so judge them against the data
rather than a script:

- **First answer:** a good one asks about alcohol. A weaker one lists every route ("if
  alcohol… otherwise…").
- **Second answer:** the right approver is Priya. Wine needs Hospitality Lead approval, the
  Hospitality Lead (Tim) is on leave, and the Approvals Register records Priya as his delegate.
  If the agent stops at "get Hospitality Lead approval", it didn't call `ask`. That's a
  useful failure to point at, and it's what the rest of the talk fixes.

**Point:** the policy says who must approve; Work IQ says who that is today.

### Demo 3: Inspect the trace

Open the trace for that run: the model calls, the tool calls and their results, and timings.
**Point:** you can see *what* it did, but not whether it was right. That's evaluation.

### Demo 4: Evaluate

Replay the evaluation output (`python evaluation/evaluate.py --demo-replay "$DEMO_REPLAY_DIR/evaluation.txt"`),
then open the real run in Foundry. Show one question, its reference answer, the agent's answer,
and the judges' verdicts. Pick a failed question and open its tool calls: did the agent call
`ask` to find the employee's manager? A wrong or missing name almost always means it didn't
look anyone up.
**Point:** one question isn't evidence; the holdout is 18 versions of the same skill.

### Demo 5: Optimise

Replay `python evaluation/demo_replay.py optimize`, then open your completed run in Foundry
(the agent's **Optimize** tab). Results differ every run, so walk through how to *read* it:

1. **Baseline vs candidates, on the holdout.** The table's scores come from the holdout
   (`approvers-holdout`), questions the optimiser never trained on. An improvement under
   0.03 is noise, by Microsoft's own guidance. On the pass/fail judge alone, one of 18
   questions is worth about 0.06, so look at how many questions changed, not just the score.
2. **Practice rounds vs holdout.** Open the run's evaluations list. The `minibatch_*` runs are
   the optimiser's quick tests on 3 training questions. A candidate that improved its
   minibatch but not the holdout learned something that doesn't transfer.
3. **Read the change.** Click **View changes** on each candidate. Sort what you see into two
   piles:
   - **General changes:** for example "use `ask` to find who currently holds an approval",
     "answer first", "don't treat out-of-office notes as approval".
   - **Copied facts:** people's names, dates or amounts from the training questions.
4. **Check it.** Run `check_prompt_facts.py` on the candidate (see *Run it yourself*). It
   lists any names, amounts or dates the baseline didn't contain.

Whatever the run shows is the demo. A clear improvement made of general changes shows the
optimiser doing its job. A candidate full of copied facts that the holdout rejected shows why
you never optimise without a holdout. If you also ran the overfitting config, it produced
the second kind when we tried it, which makes a useful contrast; check what yours did.

**Point:** optimise *how the agent works* (which tool to call), not *what it says*. The
holdout decides, and a person reviews the change before it ships.

### Demo 6: The PR that goes red

Open the prepared PR. The prompt fact check fails in seconds and lists whatever names,
amounts and dates the candidate copied in. **Point:** not every check on an AI system needs an AI judge; the cheapest
check runs first.

### Production feeds the tests (slide, 1 minute)

Optionally, show continuous evaluation setup in Foundry (**Monitor → Settings → recurring
evaluations**): sampling real conversations and choosing evaluators. **Stop before enabling
it.** Live traffic has no reference answers, so use the rubric there, not the pass/fail judge.

## Run it yourself

All commands run from `sample/`.

```bash
# Evaluate any dataset (BILLABLE). Defaults to approvers-development.
EVAL_DATASET=evaluation/datasets/approvers-holdout.jsonl python evaluation/evaluate.py --wait

# Preview the evaluation request without calling Azure.
python evaluation/evaluate.py --dry-run

# Optimise (BILLABLE, about an hour). --no-prompt uses the files named in the YAML
# instead of asking for them.
azd ai agent optimize --config evaluation/optimize.yaml --no-prompt

# Check a candidate for copied facts.
python evaluation/check_prompt_facts.py --baseline agent/.agent_configs/baseline \
  --candidate path/to/candidate --data agent/data/*.json

# Rebuild the roster and the three datasets (deterministic).
python evaluation/generate_approver_data.py
```

Evaluator definitions are `evaluation/purchasing-next-action.json` (pass/fail against the
reference answer) and `evaluation/purchasing-demo-rubric.json` (weighted rubric).
`evaluate.py` registers them if missing. To use an edited definition, register it as a new
version.

## CI/CD

| Workflow | Trigger | Runs | Blocks? |
| --- | --- | --- | --- |
| `agent-pr.yml` | Pull request | Lint, prompt fact check, then the development set vs baseline | Yes |
| `agent-main.yml` | Merge to main | Holdout vs baseline | No, it warns |
| `agent-release.yml` | Manual or `v*` tag | Drift set (must pass), then approval via the `production` environment | Yes |

All three call `_agent-eval.yml`. **First run:** trigger each workflow manually with
**write_baseline** ticked, then commit each downloaded baseline to
`sample/evaluation/baselines/<dataset>.json`.

**GitHub setup:**

- Create two environments: `demo` (used for deploying and evaluating; require a reviewer
  before allowing checked-out code to use Azure) and `production` (add yourself as a required reviewer).
- The companion Bicep can create a user-assigned managed identity with OIDC subject
  `repo:<owner>/<repo>:environment:demo`. It grants project-level **Contributor** and
  account-level **Foundry User** (also inherited by the project), not subscription-wide access.
  This identity deploys and evaluates the existing agent; it cannot provision infrastructure
  or grant roles. The `production` approval job does not sign in to Azure.
- Set these variables on the `demo` environment: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`,
  `AZURE_SUBSCRIPTION_ID`, `AZURE_ENV_NAME`, `AZURE_LOCATION`, `AZURE_AI_PROJECT_ID`,
  `FOUNDRY_PROJECT_ENDPOINT`.

Set azd's `GITHUB_REPOSITORY` to the intended `owner/repo`, including your fork, and
run the companion deployment below. Its `githubClientId` and `githubTenantId` outputs
provide the first two variables. Configure GitHub after that deployment, from `sample/`:

```bash
GITHUB_REPOSITORY="$(azd env get-value GITHUB_REPOSITORY -e "$ENVIRONMENT")"
RESOURCE_GROUP="$(azd env get-value AZURE_RESOURCE_GROUP -e "$ENVIRONMENT")"
gh variable set AZURE_CLIENT_ID --env demo --repo "$GITHUB_REPOSITORY" \
  --body "$(az deployment group show --name demo-monitoring --resource-group "$RESOURCE_GROUP" \
    --query properties.outputs.githubClientId.value -o tsv)"
gh variable set AZURE_TENANT_ID --env demo --repo "$GITHUB_REPOSITORY" \
  --body "$(az deployment group show --name demo-monitoring --resource-group "$RESOURCE_GROUP" \
    --query properties.outputs.githubTenantId.value -o tsv)"
gh variable set AZURE_ENV_NAME --env demo --repo "$GITHUB_REPOSITORY" --body "$ENVIRONMENT"
for key in AZURE_SUBSCRIPTION_ID AZURE_LOCATION AZURE_AI_PROJECT_ID FOUNDRY_PROJECT_ENDPOINT; do
  gh variable set "$key" --env demo --repo "$GITHUB_REPOSITORY" \
    --body "$(azd env get-value "$key" -e "$ENVIRONMENT")"
done
```

Only the exact repository and `demo` environment are trusted; fork pull requests do
not run the Azure job. A fork owner must provision their own identity and GitHub
environment variables. Do not approve Azure access for unreviewed PR code.

Every evaluation deploys over the one demo agent, so don't run two workflows at once (they
share a concurrency group).

## First-time setup

<details>
<summary>Provision a new environment</summary>

You need Python 3.13, `uv`, Azure CLI and azd 1.35.0, plus permission to create resources
and assign roles. Check model quota in your region first. `azure.yaml` requests GPT-5.4-mini
(400) and GPT-5.5 (100).

```bash
az login && azd auth login
azd extension install azure.ai.agents --version 1.0.0-beta.13
azd extension install azure.ai.projects --version 1.0.0-beta.8
uv venv --python 3.13
uv pip install --require-hashes -r agent/requirements.txt -r requirements-dev.txt

ENVIRONMENT="agent-evaluation-demo-<unique>"
azd env new "$ENVIRONMENT" --subscription "<subscription-id>" --location australiaeast
azd provision -e "$ENVIRONMENT" --no-prompt
```

Then deploy `infra/monitoring.bicep` for Application Insights and evaluator access. Pass
your own object ID as `evaluatorPrincipalId`, so the cloud judges can call GPT-5.5.
To also provision GitHub OIDC, set the fork-aware azd repository variable and pass it
as `githubRepository`. This requires permission to create managed identities and
role assignments, but no Microsoft Graph directory permissions:

```bash
azd env set GITHUB_REPOSITORY "<owner>/<repo>" -e "$ENVIRONMENT"
PROJECT_ID="$(azd env get-value AZURE_AI_PROJECT_ID -e "$ENVIRONMENT")"
ACCOUNT_ID="${PROJECT_ID%/projects/*}"
az deployment group create --name demo-monitoring \
  --resource-group "$(azd env get-value AZURE_RESOURCE_GROUP -e "$ENVIRONMENT")" \
  --template-file infra/monitoring.bicep \
  --parameters environmentName="$ENVIRONMENT" accountName="${ACCOUNT_ID##*/}" \
    projectName="${PROJECT_ID##*/}" \
    evaluatorPrincipalId="$(az ad signed-in-user show --query id -o tsv)" \
    githubRepository="$(azd env get-value GITHUB_REPOSITORY -e "$ENVIRONMENT")"
```

For monitoring-only setup, omit the `GITHUB_REPOSITORY` command and `githubRepository`
parameter. For an already provisioned project, use the same companion deployment;
do not rerun `azd provision` just to add GitHub authentication.

Allow a few minutes for role assignments to take effect, then deploy the agent and check it:

```bash
azd deploy purchasing-advice-demo -e "$ENVIRONMENT" --no-prompt
azd ai agent doctor -e "$ENVIRONMENT"
```

</details>
