# From prompt to production: presenter playbook

A purchasing-advice agent in Microsoft Foundry, taken from a first prompt to a gated release.
The deck is `presentation/deck.html` (or `presentation.pptx`). This page covers four things:
setting up from nothing, preparing for the day, what to show on stage, and how the CI/CD works.

## The agent

`purchasing-advice-demo`: Microsoft Agent Framework, GPT-5.4-mini (low reasoning), hosted in
Foundry. It **advises**; it can't approve, buy or contact anyone. Its three tools are local
stand-ins shaped like the Microsoft IQ tools:

| Tool | Stands in for | Answers |
| --- | --- | --- |
| `knowledge_base_retrieve` | Foundry IQ | Policies. Hybrid search: keywords plus embeddings, top 5 |
| `ask` | Work IQ | People: roles, leave, recorded delegations, messages. Like real Work IQ, it also returns the manager or role holder a question is about |
| `search_ontology` | Fabric IQ | The department's budget (a fixed value) |

> Foundry IQ: **the rules**. Fabric IQ: **the budget left**. Work IQ: **who can approve today**.

## What's where

| Path | Contents |
| --- | --- |
| `sample/agent/` | Agent code, tools, baseline config (`.agent_configs/baseline/`), data in `data/` |
| `sample/agent/data/policy_embeddings.json` | Policy vectors for hybrid search. Rebuild with `python agent/build_embeddings.py` after editing a policy |
| `sample/evaluation/datasets/` | The three test sets (below) |
| `sample/evaluation/candidates/` | The optimiser's candidate (`optimiser-0.691/`) and a reviewed version (`reviewed/`) |
| `sample/evaluation/overfitting-demo/` | An early optimiser run, kept as an exhibit of overfitting |
| `sample/infra/` | `main.bicep` (Microsoft's generated Foundry template) plus `modules/monitoring.bicep`, and the azd hooks |
| `.github/workflows/` | PR gate and main-to-release promotion, sharing one evaluator workflow |

**The three test sets** are generated by `evaluation/generate_approver_data.py`, which works out
every reference answer from the roster, so answers can't contradict the data.

| Set | File | Questions | Used by |
| --- | --- | --- | --- |
| Development | `approvers-development.jsonl` | 34 | Optimiser training; PR gate |
| Holdout | `approvers-holdout.jsonl` | 22 | Optimiser validation (Foundry's `validation_dataset`); merge to main |
| Drift | `approvers-drift.jsonl` | 8 | Release gate only. Never give it to the optimiser |

Development and holdout use different departments, people and dates. Both include harder
cases: purchases over $5,000 (Category Manager route), a missing total, "approve it and
order it", and days when a delegation has ended but the manager isn't back.

## First-time setup

One `azd up` builds everything: Foundry account, project, models, Application Insights, the
agent, and the identity GitHub Actions signs in with. Allow 15-20 minutes.

**You need:**

- Python 3.13, `uv`, Azure CLI, azd 1.35 or later, and the GitHub CLI.
- An Azure subscription where you can create resources **and assign roles**, with model quota
  in Australia East for GPT-5.4-mini (400), GPT-5.5 (300, for the judges) and
  text-embedding-3-small (50).
- Co-presenters: your own **fork** of the repository, cloned from the fork, with **Actions
  enabled** on it (the fork's Actions tab has a button; GitHub disables them on forks).

**Steps,** from `sample/`:

```bash
az login && azd auth login && gh auth login      # gh must be signed in before azd up
azd extension install azure.ai.agents --version 1.0.0-beta.13
azd extension install azure.ai.projects --version 1.0.0-beta.8
azd extension install azure.ai.connections --version 1.0.0-beta.9
uv venv --python 3.13 && source .venv/bin/activate
uv pip install --require-hashes -r agent/requirements.txt -r requirements-dev.txt

azd env new my-demo --location australiaeast
azd up
export FOUNDRY_PROJECT_ENDPOINT="$(azd env get-value FOUNDRY_PROJECT_ENDPOINT)"
python evaluation/evaluate.py --register-only  # register judges; no scoring run
```

`azd up` asks one question: the GitHub repository. Press Enter to accept your clone's `origin`.
Then it:

1. Looks up your repository's IDs and saves the exact identity GitHub will present.
2. Provisions everything in `infra/main.bicep`, including the GitHub Actions identity.
3. Creates the Application Insights connection and deploys the agent.
4. Gives the agent's own identity the role it needs for embeddings.
5. Creates two GitHub environments in your repository: `demo` (with the seven Azure
   variables) and `production` (you as required reviewer).

**Check it worked:**

```bash
export FOUNDRY_PROJECT_ENDPOINT="$(azd env get-value FOUNDRY_PROJECT_ENDPOINT)"
azd ai agent invoke purchasing-advice-demo --new-session --new-conversation \
  'Today is 3 November 2026. I'\''m Talia Cohen in Quality Assurance. Can I buy conference-room speakers for $1,060? I'\''ve got a supplier quote.'
gh variable list --env demo
```

The answer should say Amara Nwosu is on leave until 9 November with no delegation. In the
agent's trace, the policy search should show `"search_mode": "hybrid"`. If it says `keyword`,
read its `fallback_reason` (see *Troubleshooting*).

**Then set the bars for the pipelines.** Each workflow runs one test set and compares it with
its own saved result, called a **baseline**: the bar that later runs must not fall below.

| Workflow | Test set | Its baseline file | It's the bar for |
| --- | --- | --- | --- |
| Agent PR gate | Development (34) | `approvers-development.json` | Pull requests (blocks) |
| Agent promotion | Holdout (22) | `approvers-holdout.json` | Main candidates (blocks promotion) |
| Agent promotion | Drift (8) | `approvers-drift.json` | Releases (blocks) |

Setting a bar is explicit: use **write_baseline** in the PR workflow, or **baseline-holdout**
or **baseline-drift** in the promotion workflow. It saves the scores and dataset/judge
fingerprints instead of comparing. Baseline modes never release. Download and commit the artifact.
Normal runs fail if the baseline is missing or incompatible, except for the first-release drift
bootstrap described below; that bar requires separate acceptance before release.
From `sample/`, for the two you need first (these evaluations are billable):

```bash
gh workflow run agent-pr.yml --ref main -f write_baseline=true
gh workflow run agent-main.yml --ref main -f mode=baseline-holdout
# About 10 minutes each. Watch with: gh run list --limit 4

for pair in agent-pr:development agent-main:holdout; do
  RUN=$(gh run list --workflow ${pair%%:*}.yml --limit 1 --json databaseId --jq '.[0].databaseId')
  gh run download "$RUN" --name baseline-approvers-${pair#*:} --dir evaluation/baselines
done
ls evaluation/baselines        # approvers-development.json  approvers-holdout.json
git add evaluation/baselines && git commit -m "CI baselines" && git push
```

If a download says "no artifact matches", check that the run succeeded in a baseline mode.
For a replacement, download to a temporary folder first, review it,
then replace the committed file; do not discard the accepted scores before a new run succeeds.

From then on, every run of those workflows **compares** with the committed baseline. The
pipeline never moves its own bar: to accept new scores on purpose, use the appropriate baseline
mode, then download and commit as above. The first promotion can create the drift bar after
passing holdout and dev review. Every drift next-action case must pass, with no unscored rows.
Review the scores and artifact, then **Accept drift baseline and approve release** in GitHub.
Download and commit the accepted artifact before promoting again: once a release agent exists,
a missing bar is an error, not permission to bootstrap again.

To establish the drift bar separately without releasing:

```bash
gh workflow run agent-main.yml --ref main -f mode=baseline-drift
# Download baseline-approvers-drift from that successful run, review it, then commit it.
```

Every drift next-action case must pass even when creating its baseline. Legacy reports without
provenance require a fresh accepted run; do not retrofit fingerprints onto old scores.

## Before the talk

Evaluations take about 10 minutes and optimisation about an hour, so everything slow happens
beforehand. On stage you open prepared runs in Foundry; only two things run live.

1. **Holdout evaluation** in your environment:
   `EVAL_DATASET=evaluation/datasets/approvers-holdout.jsonl python evaluation/evaluate.py --wait`.
   Note the score; yours will differ from ours. Run it twice: the difference between the two
   runs is your noise level, and the floor for believing any change.
2. **Optimiser run**:
   `azd ai agent optimize --config evaluation/optimize.yaml --no-prompt`. Review the best
   candidate (see Demo 5) and run the fact check on it.
3. **The three pull requests for Demo 6**. Each gate deploys its own `-pr-<number>` agent,
   leaving the original agent and its optimiser run untouched. Leave them open for the demo;
   see *Demo 6* for the commands.
4. **Rehearse the Demo 2 question** three times and note what it says.
5. **Screenshot every portal page you'll show:** the trace, the holdout run with a failing
   row, the Optimize tab, **View changes** on the instructions and on the `ask` tool
   description, and the GitHub run. They're your backup if the network fails.
6. **Open the tabs:** model comparison, the agent, the holdout run, the Optimize run,
   GitHub Actions. And a terminal in `sample/` with the venv active and
   `FOUNDRY_PROJECT_ENDPOINT` exported.

### Demo 1: Model choice (2 minutes)

One view in Foundry: the model comparison, with Model Router mentioned in a sentence.
**Point:** the first model is a hypothesis; evaluations are what let you change it later.
Move on quickly; the rest of the session is how you'd test that hypothesis.

### Demo 2: Run the starting agent

Ask the dinner question, then reply *"Yes, there will be wine."*

```bash
azd ai agent invoke purchasing-advice-demo --new-session --new-conversation \
  'Today is 13 October 2026. Can I book a team dinner for six this Thursday? It'\''s about $540, and my manager'\''s approved it.'
```

Expected: the manager's approval doesn't cover it. With wine, a dinner needs Hospitality Lead
approval; Tim is on leave, and the Approvals Register records Priya as his delegate. That's Work
IQ doing its job. (The slide shows the same question without the date; the command needs the
date so the answer is reproducible.)

Then ask the harder one:

```bash
azd ai agent invoke purchasing-advice-demo --new-session --new-conversation \
  'Today is 21 October 2026. I'\''m Marcus Webb in Engineering. Can I buy a video-conferencing system for the boardroom for $6,800? I'\''ve got two supplier quotes.'
```

The right answer: over $5,000 needs Category Manager approval; Marco is away until 2 November
with no delegate, so wait or ask Purchasing. Leah Fischer's delegation covers line-manager
approval only. **The agent sometimes gets this right and sometimes doesn't, and that's the
point either way:**

- Wrong (names Leah): "It used Work IQ, checked leave, found the delegation, cited everything,
  and it's wrong. It asked the wrong question."
- Right: "Good answer. But it's one run. How often does it get this right?"

Both lead to the same line: **one answer isn't evidence; evaluation is.**

### Demo 3: Inspect the trace

Open the trace of the call you just made: model calls, tool calls with their inputs and
results, timings. Show `"search_mode": "hybrid"` in the policy search and the manager's
record coming back from `ask`.
**Point:** you can see *what* it did, but not whether it was right. That's evaluation.

### Demo 4: Evaluate

Open your prepared holdout run in Foundry and click a failing question. Read the judge's
reason: it describes what the tools did, not just that the answer was wrong. Which questions
fail varies from run to run; in ours, the over-$5,000 ones did, sending the employee to their
line manager instead of the Category Manager, the same failure as Marcus.

Then the story behind the numbers, from building this: with our first mock search tool the
baseline scored 12 of 18; fixing two tools, not the prompt, took it to 18 of 18, so we wrote
harder questions. Then state your own noise level from the two baseline runs: only trust a
change bigger than that.
**Point:** fix the tools first; measure across many questions; read failures, not averages.

### Demo 5: Optimise

Open the agent's **Optimize** tab and your prepared run. Every run differs, so read it rather
than following a script:

1. **The score change on the holdout.** By Microsoft's scale, under 0.03 is noise and 0.03-0.10
   moderate. Also count how many questions changed, using your noise level from the two
   baseline runs.
2. **View changes** on the best candidate, in the instructions **and the tool descriptions**,
   and sort what you find:
   - **Rules worth keeping:** general behaviour, such as answer-first wording.
   - **Copied facts:** names, amounts or dates from the training questions. Look hard at the
     tool descriptions: that's where ours hid them.
   - **What's missing:** is there a rule for the failure you saw in Demo 4 (finding the role
     the policy requires)? Ours didn't have one.
3. **Run the fact check on it** (the Demo 6 command, pointed at your candidate).

If your run turns up nothing worth showing, use the candidate saved from ours,
`candidates/optimiser-0.691/`: +0.078 on the holdout, with three good rules, training names and
amounts in its tool descriptions, and no role rule.

**Point:** the score went up; that doesn't mean you ship it. A person reads the change.

### Demo 6: Three pull requests

The gate is layered: the cheapest check runs first, and the expensive ones only run on changes
that pass it. Three prepared pull requests, one per outcome:

| Pull request | What changed | What the gate does |
| --- | --- | --- |
| **Copied facts** | The optimiser's candidate (`candidates/optimiser-0.691/`) | 🔴 **1. Offline checks** fails in seconds on the fact check. No evaluation runs |
| **"Speed up: skip the Work IQ lookup"** | Step 3 says approvals always go to the line manager; no availability check (`candidates/regressed/`) | 🔴 **2. Development set** fails: leave, delegation and Category Manager questions break. The summary shows the drop |
| **Reviewed optimiser rules** | The candidate's good rules, no copied facts, plus the missing role rule (`candidates/reviewed/`) | 🟢 Passes: same or better than the baseline |

**Showing the improvement live:** don't pick a question by hunch (our "sure to fail" question
passed on the day). Run the holdout twice with each prompt and let `compare_runs.py` find the
questions the baseline failed every time and the reviewed prompt passed every time; ask one of
those with each prompt. If none qualifies, show the improvement as a rate across the questions
instead: that's the honest version.

Show them in that order, then run the fact check live to show how cheap it is:

```bash
python evaluation/check_prompt_facts.py --baseline agent/.agent_configs/baseline \
  --candidate evaluation/candidates/optimiser-0.691 --data agent/data/*.json
```

**How the fact check knows what a fact is:** it's a plain script, no model. It compares the
candidate's instructions and tool descriptions with the baseline's and flags anything new that
looks like an amount (`$460`), a date (`27 October`), a record ID (`people:…`) or a name, where a
"name" is a capitalised pair that also appears in the agent's data files. It missed "Grace
already approved": a lone first name doesn't look like a name to it. That's why a person still
reads the change.

**Points to land:**
- Not every check on an AI system needs an AI judge; the cheapest one runs first.
- The regression looked like an optimisation. Only the evaluation could tell.
- The gate doesn't need you to *beat* the baseline, only not to fall below it by more than the
  normal wobble.
- A red check blocks merging only if a ruleset on `main` requires it. Admins can still bypass,
  and every bypass is recorded: the gate stops accidents, and puts a name on deliberate calls.

**Preparing the PRs** (after the optimiser has finished), from `sample/`:

```bash
open_pr() {  # branch, folder, title, body
  git checkout main && git checkout -b "$1"
  cp evaluation/candidates/$2/instructions.md agent/.agent_configs/baseline/
  [ "$2" = optimiser-0.691 ] && cp evaluation/candidates/$2/tools.json agent/.agent_configs/baseline/
  git commit -am "$3" && git push -u origin "$1" && gh pr create --title "$3" --body "$4"
}
open_pr demo/optimiser-candidate optimiser-0.691 "Try the optimiser's candidate" "Best candidate from the Agent Optimizer run."
open_pr demo/skip-workiq-lookup regressed "Speed up: skip the Work IQ availability lookup" "Saves a tool call per question: approvals go to the line manager."
open_pr demo/reviewed-candidate reviewed "Reviewed optimiser rules: find the required role, answer first" "The optimiser's good rules without its copied facts, plus the rule it missed."
git checkout main
```

## CI/CD

Two entry points: a PR gate and a main-to-release promotion workflow. Both use `_agent-eval.yml`
to run a test set against its committed baseline. Everything uses the existing Foundry project;
agent names isolate deployments, not separate projects.

| Target | Agent name | Purpose |
| --- | --- | --- |
| Original demo | `purchasing-advice-demo` | Live questions and manual optimisation; CI never deploys here |
| PR | `purchasing-advice-demo-pr-<number>` | Development gate; manual holdout checks of that PR |
| Main candidate | `purchasing-advice-demo-dev` | Holdout and drift gates |
| Approved release | `purchasing-advice-demo-release` | Deployed only after holdout, production review and drift |

The azd service key stays `purchasing-advice-demo`. CI uses the runner's `yq` to set its
deployed name and hosted `AGENT_NAME` in that runner's checkout before deployment: the pinned
extension validates the name before expanding variables. The evaluator targets the same name.
The committed YAML retains the original demo for local commands. The embedding hook uses the
service key to read the newly deployed agent's identity.

**The PR gate, step by step:** lint, a dry run of the evaluation request, and (on pull
requests) the prompt fact check, all in seconds without Azure. Then sign in, deploy,
evaluate, and compare. The workflow starts for every PR so required checks are always reported.
If the only changed paths are `presentation/` or `PLAYBOOK.md`, the cloud job is explicitly
skipped: no deployment or model evaluation. Every other path, including sample code, prompts,
tools, data, dependencies and CI configuration, requires evaluation. Manual runs always evaluate;
missing or unreadable comparison revisions fail rather than skipping. Renames check both paths.
Forks still cannot run cloud evaluation; a fork's presentation/playbook-only PR can report the
skipped check, while an agent-affecting fork PR needs a trusted branch in the repository.

**How the comparison works:** the baseline is a committed file,
`sample/evaluation/baselines/<test set>.json`, holding each judge's average from an accepted
run. PRs read it from their exact base revision, not from the proposed change. Before any cloud
calls, the dataset and local judge fingerprints must match the baseline. Registered judge
definitions must also match the local JSON; evaluation requests pin the resolved judge versions,
and reports record those versions. `compare_to_baseline.py` fails if any judge's average drops by more than the tolerance
(0.07 on the PR gate: about two questions, our measured noise). The release gate also fails
on any single failed row.

**Main is a production candidate:** every relevant push to `main` starts promotion:
deploy `-dev`, pass the holdout gate, then pause at the `production` environment so a reviewer
can inspect the dev agent. That approval authorises the drift test on the same deployment,
not the release. Every drift next-action case must pass, with no unscored rows. After drift,
**Approve release** is a second protected job. On a first release with no committed drift
baseline, it instead says **Accept drift baseline and approve release**. A failure stops
promotion, not the already merged commit. Only after both reviews and a successful drift gate
does a separate job deploy the same checked-out commit to `-release`; it does not resolve a newer `main`.
Configure required reviewers on the `production` environment. Release tags are not triggers.

**Manual runs:** `agent-main.yml` offers four modes. `holdout` checks without releasing;
`release` follows the full promotion path and is allowed only on `main`; `baseline-holdout`
and `baseline-drift` create artifacts without releasing. A non-main branch with an open PR
uses that PR's agent; other branches use `-check-<run ID>`. A manual PR-gate run uses
`-pr-<run ID>`, since it has no pull-request event.

```bash
# BILLABLE: check PR #8 without merging; the branch is resolved to its PR agent.
gh workflow run agent-main.yml --ref demo/reconcile-purchasing-steps -f mode=holdout
# BILLABLE: explicitly promote the current main revision, with approval before deployment.
gh workflow run agent-main.yml --ref main -f mode=release
```

**Blocking merges:** a failed check marks a PR red; it blocks merging only if a ruleset on
`main` requires the checks "1. Offline checks" and "2. Development set vs baseline / evaluate" (Settings →
Rules → Rulesets). Admins on the ruleset's bypass list can still merge; GitHub records each
bypass.

**Judge hiccups:** now and then a judge fails to score a question (usually a rate limit). The PR
and main gates allow one unscored question per judge: it's left out of the averages, named in
the log, and counted in the summary's "Not scored" column. Two or more fail the run. The release
gate allows none.

**Baselines:** one committed file per test set, in `sample/evaluation/baselines/`. Setting
them is covered in *First-time setup*. A single run is noisy (the same agent can score a question
or two differently tomorrow), which is why the gate allows a tolerance and why a person, not the
pipeline, decides when the bar moves. When you set one, run it twice if you can: if the two runs
differ by more than the tolerance, widen it for that test set.
Changes to questions, references, judge definitions or scoring configuration require an explicit
baseline refresh. A different judge version with an identical definition remains comparable.

**Environments and concurrency:** there's one Foundry project. In GitHub, `demo` holds Azure
sign-in and variables; two sequential jobs use `production` for dev review and final release
approval. The approved deployment job still
authenticates through `demo`, matching the existing OIDC trust; no new federation is needed.
Promotion runs on the same branch queue, holding `-dev` stable through both evaluations and reviews.
Evaluations targeting the same agent also queue, so a PR gate and manual holdout cannot overwrite
each other mid-evaluation. Different PRs can run independently but share model quota.
Runner jobs use `ubuntu-latest`. PR and check agents are not automatically deleted; stop or
remove them deliberately after the demo to manage hosting costs.

To evaluate a different existing agent locally, set the evaluator's shell variable:

```bash
export AGENT_NAME=purchasing-advice-demo-dev
# Unset AGENT_NAME before live questions or manual optimisation.
```

Local deployment still uses the literal name and hosted environment in `azure.yaml`;
setting a shell or azd environment variable alone does not rename the deployed agent.

`evaluation/optimize.yaml` deliberately retains the original demo agent as its target; changing
the deployment target does not silently redirect optimisation.

## Run it yourself

All from `sample/`, with the venv active and `FOUNDRY_PROJECT_ENDPOINT` exported.

```bash
# Evaluate a test set (BILLABLE). Defaults to development.
EVAL_DATASET=evaluation/datasets/approvers-holdout.jsonl python evaluation/evaluate.py --wait

# Explicitly register changed judges without submitting an evaluation.
python evaluation/evaluate.py --update-evaluators --register-only
# Then refresh and commit the affected baselines using the explicit baseline modes.

# Optimise (BILLABLE, about an hour).
azd ai agent optimize --config evaluation/optimize.yaml --no-prompt

# Check a candidate for copied facts (no Azure).
python evaluation/check_prompt_facts.py --baseline agent/.agent_configs/baseline \
  --candidate path/to/candidate --data agent/data/*.json

# What did a change actually fix? Compare runs question by question (several per side is
# better: a question only counts if it gave the same result in every run).
python evaluation/compare_runs.py --list                       # find runs: EVAL_ID:RUN_ID
python evaluation/compare_runs.py --a OLD_RUN_1 OLD_RUN_2 --b NEW_RUN_1 NEW_RUN_2
#   prints: fixed by B, broken by B, flaky, and the text of the fixed questions
#   (good to ask live). Exported .jsonl files from Foundry work as runs too.

# Rebuild the roster and test sets (deterministic), or the policy embeddings.
python evaluation/generate_approver_data.py
python agent/build_embeddings.py          # --check verifies them without Azure
```

## Lessons learned

What we found building this. Results vary between runs; these are what we saw.

- **Fix the tools first.** With a keyword-only policy search, the general purchasing policy
  ranked 4th to 9th for the agent's queries, and 4 of 6 failures were the search, not the
  agent. Fixing the search and one Work IQ lookup took the holdout from 12/18 to 18/18 with
  no prompt change.
- **Make mocks behave like the real thing.** We checked our Work IQ stand-in against real
  Work IQ: the real one answers about the manager in one question; ours stopped a step short.
  A mock that's too weak teaches the optimiser to work around problems production won't have.
- **When everything passes, your tests are too easy.** At 18/18 the optimiser had nothing to
  do. The sets had no amounts over $5,000, no missing totals, no "approve it for me".
- **Check the questions, not just the answers.** The judge flagged "invented a blocker" on
  "already approved" questions; the questions were ambiguous because the manager was on leave
  that day. We fixed the generator, not the agent.
- **Small sets are noisy.** The same agent scored 18 and 17 of 18 on two runs. Trust changes
  of two questions or more.
- **The optimiser hides memorising where reviewers don't look.** Our best candidate put
  training names and amounts into *tool descriptions*. Read every file it changed, and run
  the fact check.
- **Tell the optimiser why, not just whether.** It learns from the judge's reason. Once the
  reason described tool behaviour ("didn't check the manager's leave"), candidates proposed
  more general rules, though our best one still copied some facts.
- **Diagnose grounding before optimising behaviour.** Work IQ and the other IQ tools expose
  fixed interfaces: optimise how the agent queries them and uses their evidence. With our early
  broken mock search the score rose by copying facts into the prompt, not by repairing retrieval.
  A better score is not proof that the grounding problem is solved (see Microsoft's lesson 6).

Further reading: Microsoft's [Six lessons for reliable agent optimizer gains](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/six-lessons-for-reliable-agent-optimizer-gains-on-harder-agents/4551357)
and [Do Agent Optimizers Compound?](https://arxiv.org/abs/2607.14004).

| Symptom | Cause and fix |
| --- | --- |
| Trace shows `"search_mode": "keyword"` | Read `fallback_reason`. A 401 means the agent's identity lacks its role (new grants take about 10 minutes); re-run `azd deploy`, whose hook grants it. "stale" means a policy changed: run `python agent/build_embeddings.py` |
| GitHub sign-in fails: "No matching federated identity record" | The identity doesn't trust the subject GitHub sent. Sign in to `gh`, then `azd provision` (the hook looks up your repository's IDs) |
| `azd up` asks nothing and fails: `githubRepository` not provided | `azd env set GITHUB_REPOSITORY <owner>/<name>`, then `azd up` |
| GitHub variables missing after `azd up` | `gh` wasn't signed in. `gh auth login`, then `azd hooks run postprovision` |
| CI: "Extension required … Foundry Connections" | The workflow installs it; if you change versions, keep `_agent-eval.yml` and `azure.yaml` in step |
| A new workflow run waits | Another evaluation holds that agent, or a main promotion awaits approval. Finish or cancel that run, or wait |
| Gate says baseline has no provenance or inputs differ | Run the appropriate workflow's baseline mode on a known-good revision, then review and commit the artifact. Never add today's fingerprints to old scores |
| Registered evaluator differs from local JSON | Deliberately register the change with `--update-evaluators --register-only`, then refresh the affected baselines |
| Evaluation fails: "did not score N question(s)" | The judge model was rate-limited; the log names the questions and the error. Re-run, and if it recurs raise GPT-5.5's capacity under `ai-project` in `azure.yaml`, then `azd provision` |
| Model deployment fails on quota | Lower the capacities under `ai-project` in `azure.yaml`, or free quota elsewhere |

**Things that surprised us, for anyone editing the infrastructure:** project connections must
be `azure.ai.connection` services in `azure.yaml`, not Bicep resources; the Foundry provider
camel-cases custom output names (keep our outputs camelCase); `azd env get-value` prints
"key not found" on standard output, so scripts must test its exit code; and the hosted agent
calls models directly only through the account's `cognitiveservices.azure.com` host.
