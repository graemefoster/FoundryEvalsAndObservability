# From prompt to production: presenter playbook

A purchasing-advice agent in Microsoft Foundry, taken from a first prompt to a gated release.
The deck is `presentation/deck.html` (or `presentation.pptx`). Every command used on stage is in
`sample/demo-commands.sh`.

## The agent

`purchasing-advice-demo`: Microsoft Agent Framework, GPT-5.4-mini (low reasoning), hosted in
Foundry. It **advises**; it can't approve, buy or contact anyone. Its tools are local stand-ins
shaped like the Microsoft IQ tools; no real IQ is connected.

| Tool | Stands in for | Answers |
| --- | --- | --- |
| `knowledge_base_retrieve` | Foundry IQ | Policies (hybrid search: keywords plus embeddings) |
| `ask` | Work IQ | Roles, leave, recorded delegations, messages |
| `search_ontology` | Fabric IQ | The department's budget |

## What's where

| Path | Contents |
| --- | --- |
| `sample/agent/` | Agent code, tools, baseline config (`.agent_configs/baseline/`), data |
| `sample/evaluation/` | Evaluation and comparison scripts, judges, `optimize.yaml`, baselines |
| `sample/evaluation/datasets/` | The three test sets, generated by `generate_approver_data.py` |
| `sample/evaluation/candidates/` | Saved configs: manually improved `reviewed/`, deliberately bad `regressed/`, older optimiser exhibit `optimiser-0.691/` |
| `sample/infra/` | Foundry template, monitoring module and azd hooks |
| `.github/workflows/` | PR gate and main-to-release promotion |
| `presentation/rehearsal/` | Optional rehearsal coach for the HTML deck |

| Test set | Questions | Used by |
| --- | --- | --- |
| Development | 34 | Optimiser training; PR gate |
| Holdout | 22 | Optimiser validation (it influences selection); merge to main |
| Drift | 8 | Release gate only. Never give it to the optimiser |

## First-time setup

You need Python 3.13, `uv`, Azure CLI, azd 1.35+ and the GitHub CLI; a subscription where you
can create resources and assign roles; and Australia East quota for GPT-5.4-mini (400),
GPT-5.5 (300) and text-embedding-3-small (50). Co-presenters: use your own fork with Actions
enabled.

From `sample/` (allow 15-20 minutes):

```bash
az login && azd auth login && gh auth login      # gh must be signed in before azd up
azd extension install azure.ai.agents --version 1.0.0-beta.13
azd extension install azure.ai.projects --version 1.0.0-beta.8
azd extension install azure.ai.connections --version 1.0.0-beta.9
uv venv --python 3.13 && source .venv/bin/activate
uv pip install --require-hashes -r agent/requirements.txt -r requirements-dev.txt

azd env new my-demo --location australiaeast
azd up                                           # accept your clone's origin as the repository
export FOUNDRY_PROJECT_ENDPOINT="$(azd env get-value FOUNDRY_PROJECT_ENDPOINT)"
python evaluation/evaluate.py --register-only    # register judges; no scoring run
```

`azd up` builds the Foundry project, models, Application Insights, the agent, the GitHub Actions
identity, and the GitHub environments `demo` (Azure variables) and `production` (you as reviewer).
Check it with the Demo 2 question: the trace's policy search should show `"search_mode": "hybrid"`.
The `requirements*.txt` files are exported from `uv.lock` (command at the top of each); install
from them, as CI does.

**Baselines.** Each gate compares a test set with a committed baseline in
`evaluation/baselines/`. The pipeline never moves its own bar; a person does. The repository
ships with baselines that work in a new project, so you can skip this. Replace them when you
change questions, references or judges, or want your own bar. From `sample/` (billable, about
10 minutes each; the two promotion runs queue one after the other):

```bash
gh workflow run agent-pr.yml --ref main -f write_baseline=true
gh workflow run agent-main.yml --ref main -f mode=baseline-holdout
gh workflow run agent-main.yml --ref main -f mode=baseline-drift
```

Wait until `gh run list --limit 3` shows all three completed, then download and commit them.
The push starts a promotion to release.

```bash
rm -f evaluation/baselines/*.json      # gh won't overwrite existing files
gh run download --name baseline-approvers-development --dir evaluation/baselines
gh run download --name baseline-approvers-holdout --dir evaluation/baselines
gh run download --name baseline-approvers-drift --dir evaluation/baselines
git add evaluation/baselines && git commit -m "CI baselines" && git push
```

Never copy new fingerprints onto old scores; a changed test set or judge needs fresh baselines.

## Before the talk

Evaluation takes about 10 minutes and optimisation about an hour, so prepare them beforehand.

1. Run the holdout evaluation twice. The difference is your noise level.
2. Run the optimiser, review the best candidate and run the fact check on it.
3. Prepare Demo 6: a reviewed candidate promoted to release, and the bad-prompt PR left
   blocked (`open_pr` in `demo-commands.sh`).
4. Rehearse the Demo 2 questions three times.
5. Screenshot every portal page you'll show, as a network fallback.
6. Open tabs: model comparison, the agent, the holdout run, the Optimize run, GitHub Actions,
   and a terminal in `sample/` with the venv active and `FOUNDRY_PROJECT_ENDPOINT` exported.

**Demo 1.** The model comparison. The first model isn't a lock-in; evaluations tell you when to change.

**Demo 2.** Ask the dinner question, then *"Yes, there will be wine."* Expected: the manager's
approval doesn't cover it; wine needs the Hospitality Lead, Tim is on leave, and Priya is his
recorded delegate. Then Marcus: over $5,000 needs the Category Manager; Marco is away until
2 November with no delegate, so wait or ask Purchasing (Leah's delegation covers line-manager
approval only). Right or wrong, the point is the same: **one answer isn't evidence.**

**Demo 3.** Open that trace: model and tool calls, inputs, results, timings. You can see *what*
it did, not whether it was right.

**Demo 4.** Open the prepared holdout run, click a failing question and read the judge's reason.
Compare development with holdout, and state your noise level. Read failures, not just averages.

**Demo 5.** Open the Optimize tab. Check the score change against noise, then **View changes** in
the instructions *and* tool descriptions: rules worth keeping, copied facts, and what's missing.
If your run has nothing worth showing, use `candidates/reviewed/` and say it was improved by hand.
The score went up; a person still reads the change.

**Demo 6.** Show the reviewed PR's journey: development passed, holdout on `-dev`, review, drift,
release approval, `-release` deployed. Then the bad-prompt PR: offline checks pass, the
development set fails, and branch protection blocks the merge. Don't merge it. The fact check is
a plain script, no model: it flags new amounts, dates, IDs and names, and missed a lone first name,
which is why a person still reads the change.

**From test cases to production.** Optionally show **Monitor → Settings** for continuous evaluation,
but don't enable it. Live traffic has no reference answers, so use the rubric there.

## CI/CD

Both workflows use `_agent-eval.yml` to deploy an agent, evaluate a test set and compare it with
the committed baseline. One Foundry project; agent names isolate deployments.

| Agent | Purpose |
| --- | --- |
| `purchasing-advice-demo` | Live questions and optimisation. CI never deploys here |
| `purchasing-advice-demo-pr-<number>` | PR gate: offline checks, then development set |
| `purchasing-advice-demo-dev` | Every push to main: holdout, review, then drift |
| `purchasing-advice-demo-release` | Deployed only after holdout, review, drift and release approval |

The gates fail on a drop bigger than the tolerance (0.07 on the PR gate, our measured noise),
not below a fixed number. The release gate fails on any failed or unscored drift case. A red
check blocks merging only if a `main` ruleset requires "1. Offline checks" and
"2. Development set vs baseline". PR agents aren't deleted automatically; remove them after the demo.

## Rehearsal coach (optional)

The HTML deck's **Rehearse** panel (`R`) times each slide, transcribes you locally with Whisper
and scores each slide's concepts with Decision-1. The deck works normally without it.

Needs Node 24+, `az login`, and `whisper-cpp` plus `ffmpeg` (`brew install whisper-cpp ffmpeg`):

```bash
mkdir -p "$HOME/.cache/whisper" && curl --fail --location \
  https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-base.en.bin \
  --output "$HOME/.cache/whisper/ggml-base.en.bin"
cd presentation/rehearsal && npm ci
DECISION_ENDPOINT="https://<account>.services.ai.azure.com/providers/microsoft/v1/systemone" \
DECISION_DEPLOYMENT="<deployment-name>" npm start
```

Open `http://127.0.0.1:4173/`, choose **Check setup**, tick consent (Decision-1 calls are
billable) and **Start rehearsal**. Pause releases the microphone; **Finish** opens a per-slide
review; **Copy for LLM** copies the transcript plus the exact request and response. Concepts are
in `src/concepts.ts`. Recordings stay in the browser tab; keep downloads out of the repository.
After code changes: `npm run build && npm test && npm run test:browser`.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Trace shows `"search_mode": "keyword"` | Read `fallback_reason`. A 401 means the agent's identity lacks its role (allow 10 minutes, then `azd deploy`). "stale": run `python agent/build_embeddings.py` |
| GitHub sign-in: "No matching federated identity record" | Sign in to `gh`, then `azd provision` |
| `azd up` fails: `githubRepository` not provided | `azd env set GITHUB_REPOSITORY <owner>/<name>`, then `azd up` |
| GitHub variables missing after `azd up` | `gh auth login`, then `azd hooks run postprovision` |
| A workflow run waits | Another evaluation holds that agent, or a promotion awaits approval |
| Baseline has no provenance or inputs differ | Run the baseline mode on a known-good revision, review and commit the artifact |
| Registered evaluator differs from local JSON | `python evaluation/evaluate.py --update-evaluators --register-only`, then refresh baselines |
| "did not score N question(s)" | Judge rate-limited. Re-run; if it recurs, raise GPT-5.5 capacity in `azure.yaml` and `azd provision` |
| Model deployment fails on quota | Lower the capacities under `ai-project` in `azure.yaml` |
